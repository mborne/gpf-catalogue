# The pivot model

One flat JSON document per resource of the catalogue, written to
`data/csw/{name}.json`. The model is defined in
[`gpf_catalogue/model.py`](../gpf_catalogue/model.py) and its JSON schema is generated by
`uv run scripts/export_schema.py` into [`pivot-schema.json`](pivot-schema.json).

## Fields

| Field | Type | Source in ISO 19115-3 | Notes |
|---|---|---|---|
| `fileIdentifier` | `string` | `mdb:metadataIdentifier/mcc:MD_Identifier/mcc:code` | Stable identifier, usable in `GetRecordById&ID=…` and in cartes.gouv.fr URLs. Never read from the `@uuid` attribute, which is empty on some records |
| `type` | `dataset` \| `series` \| `service` | `mdb:metadataScope//mcc:MD_ScopeCode/@codeListValue` | Falls back on the kind of identification block when absent |
| `title` | `string` \| `null` | `<identification>/mri:citation/cit:CI_Citation/cit:title` | `null` on the records that publish none |
| `abstract` | `string` \| `null` | `<identification>/mri:abstract` | `null` when absent |

`<identification>` is `mdb:identificationInfo/mri:MD_DataIdentification` for data, and
`mdb:identificationInfo/srv:SV_ServiceIdentification` for services. Both inherit their
citation and abstract from the same ISO type, so one code path reads both.

## Example

```json
{
  "fileIdentifier": "GeoPF_Altimetrie",
  "type": "service",
  "title": "API Géoplateforme - Calcul altimétrique",
  "abstract": "API Géoplateforme - Calcul altimétrique"
}
```

## Design rules

- **Flat.** No nesting, no sub-objects. A consumer reads a field, it does not walk a tree.
- **One shape for every resource.** A service and a dataset are the same object with a
  different `type`, rather than two classes. Splitting them would fork every consumer for
  no benefit at this size.
- **Optional rather than fabricated.** A field the catalogue does not provide is `null`.
  The pipeline never derives a title from an identifier to fill a hole.
- **Lossy by design.** The model answers "which resource is this, and what is it about?".
  Everything else stays in the harvested XML next to it.
- **camelCase in JSON, snake_case in Python.** The JSON keys stay close to the ISO
  vocabulary the metadata already uses.

## Extending it

New fields are added to `CatalogueRecord` and read through the same `_text()` helper in
[`gpf_catalogue/parse.py`](../gpf_catalogue/parse.py), which resolves the
`gco:CharacterString` / `gcx:Anchor` / `lan:PT_FreeText` alternatives in one place.
Regenerate the schema afterwards:

```bash
uv run scripts/export_schema.py
```

See [ROADMAP.md](../ROADMAP.md) for the fields planned next.
