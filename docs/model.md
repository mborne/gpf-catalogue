# The pivot model

*Author: Claude (Anthropic) — this document is AI generated, see [init.md](init.md).*

One flat JSON document per resource of the catalogue, written to
`data/csw/{name}.json`, plus every record in a single `data/catalogue.json`. The model
is defined in [`gpf_catalogue/model.py`](../gpf_catalogue/model.py) and its JSON schema
is generated by `uv run scripts/export_schema.py` into
[`pivot-schema.json`](pivot-schema.json).

## Fields

The coverage column is **measured, not estimated**, over the 326 records of the run of
2026-09-20. `uv run scripts/stats.py --format markdown` regenerates it from the current
catalogue; `stats.py` reads the field list from the model itself, so a field added to
`CatalogueRecord` is counted without being registered anywhere. See
[overview.md](overview.md) for the page that displays it.

`<identification>` below is `mdb:identificationInfo/mri:MD_DataIdentification` for data,
and `mdb:identificationInfo/srv:SV_ServiceIdentification` for services. Both inherit
their citation, contacts, keywords and extent from the same ISO types, so one code path
reads both.

`spatialScope` answers *is this a national product or a local one?* — the cheapest
filter there is, and one a bounding box does not give: 81 records declare the same
mainland France box. 136 records cite it, as one keyword anchor in an
`INSPIRE Spatial Scope` thesaurus block:

```xml
<mri:keyword>
  <gcx:Anchor xlink:href="http://inspire.ec.europa.eu/metadata-codelist/SpatialScope/national">National</gcx:Anchor>
</mri:keyword>
```

The **code** is read, never the label. They disagree: 6 records cite
`…/SpatialScope/global` under the label "National", and the labels spell two codes four
ways — `National`, `Nationales`, `Régional`, `regional`. The code is the controlled
value, the label is free text that happens to be next to it. `National` is in fact the
most frequent keyword of the catalogue, on 123 records — 117 citing the code `national`
and 6 citing `global`; faceting on the word would put those 6 in the wrong bucket, which
is the whole reason the field exists as a code. The keyword itself stays in `keywords`
exactly as published, label and all: the model does not edit what it flattens.

The thesaurus block is not matched, only the keyword's own `xlink:href` — which is
where the code lives. Not a single one of the 136 appears outside its thesaurus, and the
thesaurus title itself is published two ways (`INSPIRE Spatial Scope` and
`INSPIRE Spatial scope`), so matching on it would add a rule and buy nothing.

A code outside the five values above is logged and the field stays `null`, rather than
being guessed at from the label — the label being what disagrees with the code in the
first place.

The counts, over the 326 records: `national` 118, `global` 6, `regional` 5, `local` 4,
`european` 3, and 190 records citing nothing at all.

#### Named extents, and why `bbox` is still there

`bbox` is in decimal degrees, WGS 84, **GeoJSON order** — not the ISO order, which lists
the two longitudes then the two latitudes. It is the union of every box the record
declares, which makes it a one-comparison filter and a coarse one. `extents` is the same
information undestroyed.

The catalogue publishes one `gex:EX_Extent` per territory, each with its own box and, on
413 of the 580 boxes, a name and an ISO 3166 alpha-3 code:

```xml
<mri:extent>
  <gex:EX_Extent>
    <gex:description><gco:CharacterString>Guadeloupe</gco:CharacterString></gex:description>
    <gex:geographicElement>
      <gex:EX_GeographicBoundingBox>…</gex:EX_GeographicBoundingBox>
    </gex:geographicElement>
    <gex:geographicElement>
      <gex:EX_GeographicDescription>
        <gex:geographicIdentifier>
          <mcc:MD_Identifier>
            <mcc:authority><cit:CI_Citation><cit:title>ISO 3166 alpha 3</cit:title></cit:CI_Citation></mcc:authority>
            <mcc:code><gco:CharacterString>GLP</gco:CharacterString></mcc:code>
          </mcc:MD_Identifier>
        </gex:geographicIdentifier>
      </gex:EX_GeographicDescription>
    </gex:geographicElement>
  </gex:EX_Extent>
</mri:extent>
```

`IGNF_BD-TOPO` declares eight of them, from `FXX` to `MAF`. Their union spans
`[-63.16, -21.4, 55.85, 51.1]`, a box reaching from the Caribbean to Réunion across the
Atlantic, Africa and the Indian Ocean — **65 times the area the product describes**. 47
records declare more than one box, and the worst of them,
`ENR_CONSO-ELECTRICITE-COMMUNE`, has a union **3 519 times** the combined area of its four
territories. Keeping only the union does not merely lose detail; it states a coverage the
catalogue never claimed. So both are published: `bbox` to filter cheaply, `extents` to
answer.

Three rules follow from the shapes actually met:

- **A box missing one of its four sides is skipped**, never completed, and produces no
  extent either.
- **An extent carrying no usable box produces no entry.** 115 extents of the catalogue
  carry a description and no geometry, because they describe a *period*: labelling a
  resource with the place "Dates de publication" would be worse than saying nothing. The
  period itself is already in `temporalStart` / `temporalEnd`.
- **A name is never invented.** 167 of the 580 boxes are published with no description
  and no identifier; they are listed with `name` and `code` at `null`.

Grouping or dissolving these zones is the consumer's business, as it is for `links`.

`updateFrequency` is the `MD_MaintenanceFrequencyCode` **code**, not its label, like every
other code list value here — but it is typed `string` rather than an enumeration, because
one record publishes `quaterly` where ISO says `quarterly`. An enumeration would reject
that record, and silently correcting the spelling would put in the model something the
catalogue did not say. The counts: `notPlanned` 83, `unknown` 66, `asNeeded` 54,
`irregular` 50, `annually` 31, `monthly` 8, `continual` 5, `quarterly` 5, `weekly` 4,
`biannually` 4, `daily` 3, `completed` 1, `quaterly` 1.

When a date type appears twice, the first wins, so a rerun gives the same answer.

### What may be done with it

| Field | Type | Source in ISO 19115-3 | Coverage |
|---|---|---|---|
| `licence` | `string` \| `null` | `mco:otherConstraints` of a block declaring `mco:useConstraints` | 50.0 % |

ISO carries both as free text in the same element; what tells them apart is the sibling

The text is kept verbatim, with one exception: several records glue an anchor's target
onto its own label, so `IGNF_BD-TOPO` publishes its licence as
`Licence Ouverte / Open License (compatible ODC-BY, CC-BY 2.0)https://www.etalab.gouv.fr/…`.
When the text ends with a byte for byte repeat of its own `xlink:href`, the duplicate is
removed — nothing is invented, and the value becomes readable.

### How to reach the data

| Field | Type | Source in ISO 19115-3 | Coverage |
|---|---|---|---|
| `links` | `Link[]` | `mdb:distributionInfo/mrd:MD_Distribution//mrd:onLine/cit:CI_OnlineResource` | 98.5 % |
| `thumbnailUrl` | `string` \| `null` | `<identification>/mri:graphicOverview/mcc:MD_BrowseGraphic/mcc:fileName` | 63.2 % |

A `Link` is `{ "type": …, "url": …, "name": string｜null, "description": string｜null }`,
with `type` one of `wfs`, `wms`, `wmts`, `tms`, `download`, `capabilities`,
`documentation`, `other`.

Across the catalogue, 2 575 links over 828 distinct endpoints:

| `wfs` | `wms` | `wmts` | `documentation` | `other` | `download` | `capabilities` | `tms` |
|---|---|---|---|---|---|---|---|
| 657 | 587 | 353 | 322 | 235 | 232 | 129 | 60 |

Three rules produce that, in order:

1. **A static `capabilities.xml`** — always under `/annexes/`, behind a path no service
   segment would match — is a document, not an endpoint.
2. **`cit:protocol`**, when present. It is absent on 85 % of the links, so it cannot be
   the only signal.
3. **The URL path.** The Géoplateforme serves each protocol under its own prefix
   (`/wfs/`, `/wms-v/`, `/wms-r/`, `/wmts/`, `/tms/`, `/telechargement/`), then the file
   suffix decides: `.pdf` and friends are documentation, archives and tabular files are
   downloads. Styling files (`.qml`, `.sld`, `.qgz`) stay `other` — they describe how to
   draw a layer, not the layer.

A `?REQUEST=GetCapabilities` *query* is deliberately **not** treated as a capabilities
document: `https://data.geopf.fr/wfs/ows?…GetCapabilities` is the WFS endpoint itself,
advertised through its capabilities URL, and typing it as a document would hide the
endpoint from a consumer asking where the WFS is.

#### One entry per layer, kept flat

The catalogue publishes one `CI_OnlineResource` **per layer**, all carrying the same
endpoint URL and differing by `cit:name` and `cit:description`: `IGNF_BD-TOPO` publishes
109 WFS entries for a single WFS URL, and `IGNF_ADMIN-EXPRESS` 251 entries over 16 URLs.

Every entry is kept, one link each:

```json
{ "type": "wfs", "url": "https://data.geopf.fr/wfs/ows?…", 
  "name": "BDTOPO_V3:batiment", "description": "BD TOPO® V3 batiment" }
```

Only **exact** repeats are dropped — the same `(type, url, name, description)` published
twice, 9 entries across the catalogue. 78 records publish several entries on one
endpoint.

Earlier versions collapsed those entries on `(type, url)`, keeping the first name. That
cost the 1 179 layer names the catalogue publishes, and labelled a whole WFS service
`BDTOPO_V3:aerodrome` — which reads as *this endpoint serves aerodromes*. Losing
information is bad; stating something untrue is worse. **Grouping is a presentation
concern**, not a modelling one: the overview groups by `(type, url)` when it renders a
record, and a consumer that wants one row per endpoint can do the same in two lines.

`name` and `description` are both kept because they say different things: `name` is
machine readable (`BDTOPO_V3:batiment`, the WFS `typeName` a client actually sends),
`description` is what a reader wants ("BD TOPO® V3 batiment"). They differ on 2 212 of
the 2 243 entries carrying both. Only **4 links of the 2 575** carry neither, so nothing
but their URL says what they lead to.

### Catalogue hygiene

| Field | Type | Meaning |
|---|---|---|
| `suspectedTest` | `boolean` | The record looks like a test publication |

The Géoplateforme publishes test records next to real ones. The rule is narrow on
purpose: a record is flagged when one of its identifier, title or abstract is *entirely*
a test token (`test`, `demo`, `essai`, `lls`, …), or when its title *begins* with one.
Matching a token anywhere would flag `test_openig`, which is titled "Communes de
l'Hérault (34)" and is a real dataset.

It flags 14 of the 326 records. It is a heuristic and says so in its name: it misses
junk that looks like nothing in particular, such as the record identified `1`, titled
"Vectorisation IA", whose abstract is `blba lbla`. Flagging rather than dropping leaves
that judgement to the consumer.

## Design rules

- **Flat.** A consumer reads a field, it does not walk a tree. Multi-valued fields are
  lists of strings, not lists of objects — with two exceptions, below.
- **One shape for every resource.** A service and a dataset are the same object with a
  different `type`, rather than two classes. Splitting them would fork every consumer for
  no benefit at this size.
- **Optional rather than fabricated.** A field the catalogue does not provide is `null`,
  or `[]` for a list. The pipeline never derives a title from an identifier, never
  completes a half declared bounding box, and never guesses a licence.
- **Lossy by design.** The model answers "which resource is this, what is it about, who
  made it, and how do I reach it?". Everything else stays in the harvested XML next to it.
- **Deterministic.** Two runs over the same mirror produce the same bytes: no timestamp
  in `catalogue.json`, first value wins on every ambiguity, stable ordering everywhere.
  This is what makes catalogue drift diffable (see [ROADMAP](../ROADMAP.md) phase 5).
- **camelCase in JSON, snake_case in Python.** The JSON keys stay close to the ISO
  vocabulary the metadata already uses.

### Why links and extents are objects

`Link` and `Extent` are the two sub-objects of the model, and both earn the exception for
the same reason: their parts are only meaningful together.

An access endpoint is only usable as a `(type, url)` pair: a bare URL does not say
whether it can be queried as a WFS or merely downloaded, and a bare type is not
actionable. The alternatives both lose something real. Parallel lists — `wfs: […]`,
`wms: […]` — cannot say which name belongs to which URL, and spread seven keys across the
top of every document. A dictionary keyed by type, `links: {"wfs": […]}`, keeps one key
but loses the name too.

Names are worth keeping: "BD TOPO® EXPRESS" and "BD TOPO® DIFFERENTIEL" are two downloads
of the same resource, and only their names tell them apart. The shape is also the one a
consumer is likely to already know, being that of STAC assets and DCAT distributions.

`Extent` is the same argument applied to geography. A zone is only usable as a
`(name, bbox)` pair: four numbers do not say which territory they outline, and
"Guadeloupe" is not something a map can draw. Parallel lists — `extentNames: […]`,
`extentBoxes: […]` — would keep the values and lose the pairing, which is precisely the
information the flat `bbox` had already destroyed.

## Extending it

New fields are added to `CatalogueRecord` and read through the same `_text()` helper in
[`gpf_catalogue/parse.py`](../gpf_catalogue/parse.py), which resolves the
`gco:CharacterString` / `gcx:Anchor` / `lan:PT_FreeText` alternatives in one place.
Regenerate the schema afterwards:

```bash
uv run scripts/export_schema.py
```

Then regenerate the measured figures, rather than editing them by hand:

```bash
uv run scripts/stats.py --format markdown
```

The rule for what enters the model: **a field enters when a search or a question needs
it, not because ISO defines it.** Two fields planned in phase 2 were dropped for the
opposite reason — `srv:operatesOn` and `mdb:parentMetadata`, which would have linked a
service to the dataset it serves, appear in **zero** of the 333 records. See
[ROADMAP.md](../ROADMAP.md) for the fields planned next.
